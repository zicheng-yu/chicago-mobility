# 芝加哥天气和节假日与城市出行的关系

《大数据原理与应用》中期项目。使用 2024 年共享单车、出租车、天气、联邦节假日与社区边界，完成真实数据采集、清洗、融合、分析和可视化。

[项目仓库](https://github.com/zicheng-yu/chicago-mobility)目前公开，也可使用本地提交包提交。

## 本次结果

有效原始数据为 3,149,961,547 字节（3.150 GB），最大单源占比 63.08%。Divvy 原始运营记录 5,860,568 条，研究保留 5,583,690 条单车记录；出租车原始记录 6,480,350 条，清洗后 6,107,775 条。数据覆盖 366 天，两个主要源均逐层对账。

控制日历与天气变量后，每增加 10 mm 降水，单车日记录量的关联估计为 −18.8%（近似 95% 区间 −27.5% 至 −9.2%）。出租车估计 +1.8%，但区间跨过零。节假日的出租车记录量较少，单车估计的区间也跨过零。这些结果描述观察性关联，不能证明出行方式替代或因果关系。

完整结果见 `deliverables/`、`results/` 和 `docs/scale_audit.json`。

展示 PPT 已按课堂展示重新设计，采用城市雨夜示意封面、原生置信区间图、可编辑社区地图及热力表。当前版本为 `deliverables/展示PPT.pptx`，构建源为 `presentation/redesign_deck.mjs`，封面素材和完整生成提示词保存在 `presentation/assets/README.md`。数据、统计结果和报告内容保持原核验版本。

## 研究问题

1. 控制月份、星期与温度后，降水与两种出行方式的每日记录量有什么关系？
2. 联邦节假日与普通日期的出行记录量和小时分布有何差异？
3. 两种方式的社区分布、社区内降水日变化是否一致？

问题均依赖至少两个来源。这里只解释观察到的关联，不能据此判断某一位乘客是否由单车改乘出租车，也不能把样本记录量解释为城市全部出行需求。

## 运行

仓库附带完整融合表、质量记录、社区边界和天气辅助数据。只复现分析与图表时，安装依赖后运行 `python analysis/analyze.py` 即可；下面的完整流程会重新获取和处理两类大型运营明细。

需要 Python 3.12 或以上、可访问官方公开数据源的网络，以及约 8 GB 可用空间。首次运行主要耗时是下载数据。

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python crawler/collect.py --workers 2
python processing/build.py
python analysis/analyze.py
python processing/audit.py
python -m analysis.lineage
python docs/build_report.py
```

也可使用 `python run_pipeline.py` 依次执行全部步骤。报告生成脚本为 `docs/build_report.py`，展示文稿使用 Codex 的演示文稿运行时生成；统计分析的复现不依赖该演示文稿运行时。

单车按月、出租车按日保存。ZIP 支持续传；出租车每次最多获取 5000 条，按 trip_id 做游标分页并缓存已完成的页面，随后保留原始对象内容、仅合并外层数组为日归档。已经完整下载的日文件直接复用。未完成内容使用 `.partial`，完成后才更名，全年 366 个文件按月与官方 `count(*)` 对账。页缓存不重复计入数据规模。不完整文件不参与分析。网络或服务端错误会记录在采集日志并退避重试。

可以单独采集一个来源或月份，例如：

```bash
python crawler/collect.py --source divvy --months 1 2 --workers 2
python crawler/collect.py --source taxi --months 1 2 --workers 2
python crawler/collect.py --source aux
```

最终分析要求两个主要源均覆盖全年 12 个月，即 12 个单车文件与 366 个出租车文件。`processing/build.py` 会拒绝文件不完整的数据。

## 数据口径

- 时间：使用芝加哥当地日期和小时。出租车原始时间由发布者取整到 15 分钟，因此只做小时和日级比较；时长直接采用官方 `trip_seconds`，不用取整后的起止时刻相减。单车在夏令时切换附近的无时区时长可能有歧义，时长异常会按相同规则过滤。
- 清洗：Divvy 只保留 classic_bike 与 electric_bike，排除 electric_scooter。再去除缺少 ID 或开始时间、年份不在 2024、重复 ID、时长缺失或不在 60 秒至 24 小时范围的记录。金额、里程异常仅置缺失，不额外删除整次出行。空间未知记录仍保留在系统日级分析，只从社区分析排除。
- 文件分区：单车月度文件中可能出现上月末开始的记录。日期依据行内时间，不依据文件名；按固定文件与分块顺序对同一来源的 ID 全局去重，保留首次出现的记录。
- 空间：单车起点通过 GeoJSON 多边形匹配社区，出租车使用官方上车社区编号。边界上的点和城市范围以外的点保留为空，不用最近邻强行分配。
- 日级口径：使用两个运营系统的全部有效记录，包含社区未知或芝加哥市域之外的部分起点；社区分析只保留成功匹配市内社区的记录。因此日级量应理解为这两个系统的记录量。
- 类别字段：单车 `member_casual` 保存为 `rider_type`，出租车 `payment_type` 单独保留；两者含义不同，不作同一类别字段。社区日级网格补全缺少的组合为零，零表示该公开记录中没有对应出行，不代表真实城市需求为零。
- 天气：NOAA 奥黑尔与中途机场两个站点，先剔除有质量标志的观测，再对每日有效观测取平均。温度为每日最高和最低温的均值代理。`rain_day` 是内部字段名，实际表示日降水量至少 1 mm，包含降雪的液态当量。
- 节假日：从 OPM 的 2024 年表解析 11 个联邦节假日，优先标记节假日，其次周末，其他为普通工作日。这不代表所有居民实际休假。
- 规模：只累计两个主要源的原始明细有效字节。Divvy 按原 CSV 的实际记录字节，扣除滑板车、无效年份及重复 ID；出租车归档要求原始 ID 与日期检查通过。ZIP、分页缓存、清洗表、融合表、图像与元数据不重复计入 2 GB。统计同时列十进制 GB 和二进制 GiB。

## 方法

以月内日均量观察季节差异。用 `log(1+每日记录量)` 的普通最小二乘回归描述降水和节假日的关联，控制月份、星期、温度一次和二次项、平均风速。区间采用 7 日滞后的 Newey–West 协方差估计。系数转换为 `100×(exp(系数)−1)`，在日记录量较大的条件下近似表述为记录量百分比变化。回归不用于因果归因。

社区降水比较先按“社区、月份、星期”的日均量标准化，再比较降水日与非降水日。只展示两类全年记录均至少 1 万次的社区，减少稀疏记录的极端比例。这仍未消除温度及所有季节因素的混杂。

数据挖掘采用 KMeans，固定三个类别、随机种子 42 和 20 次初始化。对出租车日量、温度、降水和风速四个特征标准化，并报告轮廓系数。结合 Divvy 许可的使用范围，聚类仅使用出租车和 NOAA 天气；共享单车用于常规统计比较。类别只用于探索联合模式。

## 核验与复现

`docs/integration_checks.json` 对账清洗行数、日级总量、小时级总量、空间匹配数量，检测连接导致的记录倍增或丢失。`docs/cleaning_quality.json` 分月记录排除原因。`docs/weather_quality.json` 记录天气质量标志与缺失。

`docs/file_manifest.csv` 提供原始文件的字节数与 SHA-256，`docs/scale_audit.json` 检查 2 GB、主要源 200 MB、单源 80% 上限。来源平台可能修订历史数据；复现时应以文件校验值判断是否是相同快照。

完整原始数据保存在本机，不放进 Git。仓库提交代码、少量样本、融合表、图表、元数据、日志与校验信息即可。分享时请遵守 [Divvy 数据许可](https://divvybikes.com/data-license-agreement) 与芝加哥市使用条款，不把原始运营数据另行包装销售。
